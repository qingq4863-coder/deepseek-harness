# Agent Note：包候选解析保持只读

Status: implemented

[English](2026-09-09-pkg-propose.md) | 中文

## 问题

安装器规划的 §4.4 流程要求在下载或安装任何东西**之前**给出拟下载内容、版本、许可证、体积与权限，并要求两者都得到显式确认。包管理器清单已经回答「装了什么」，但还没有东西回答「安装它会怎样」，而这个答案必须来自一条恶意包名无法操纵的命令。

## 决策

`pkg_propose` 为每个管理器运行一条固定的描述探测——`winget show --id <name> --exact --disable-interactivity --accept-source-agreements`、`npm view <name> --json`、`pip index versions <name>`——各自在自己的审批决定之后。包名是唯一的模型输入：必须以字母数字开头且只含字母、数字、点、下划线、加号或连字符，并作为固定命令的单个 argv 元素传递，因此既不能变成标志也到不了 shell。每次探测经子进程 seam 解析可执行文件、记录状态与原因，并受与 `pkg_inspect` 相同的 `pkgTimeoutMs` 与输出上限约束。

结果携带管理器会安装的版本、源列出的最新版本、管理器报告时的本地已装版本（缺失不等于未安装，那个问题仍由 `pkg_inspect` 回答）、发布者、许可证、产物位置以及源公布的哈希。哈希被标注为由源报告而非已验证，因为本切片不获取也不校验产物。每个字段都经过共享清洗器，渲染文本明确说明没有下载或安装任何东西，且安装需要一次显式确认步骤。

§4.4 的安装、验证与回滚那一半是另一个决策，不是本切片的主题：执行它会同时扩大网络可达范围（获取产物）与机器变更（运行安装程序），而规划 §7 要求这类扩展必须获得显式授权。按名字安装与卸载软件包已实现为工具注册表显式审批门禁之后的固定管理器命令（见[变更 Agent Note](2026-09-09-pkg-mutation.zh.md)）；本笔记只覆盖候选结果可以报告的内容。

## 考虑过的替代方案

**把解析与安装一起实现。** 目前否决：捆绑会把一次「网络 + 变更」的能力扩展藏进只读切片里。规划的升级协议要求该扩展获得授权，而且回滚演练必须针对用户选定的软件包进行。

**在候选结果里返回确切的安装命令行。** 否决：那正是清单切片刻意扣留的变更面，而想看到该命令的调用方在安装工具存在时会在审批提示里看到它。候选结果改用结构化字段。

**让同一次探测顺带回答「是否已安装」。** 否决：只有 pip 会报告它，因此一个暗示全局答案的候选结果在 winget 与 npm 上会是错的。该问题由 `pkg_inspect` 统一回答。

## 后果

调用方可以呈现具体、有来源的候选并就此停下，模型也无法把恶意包名变成标志或命令。对抗用例钉住了名称校验（含前导连字符、路径、shell 元字符与超长名称）、不产生进程的拒绝路径、实际启动的固定 argv、失败/部分/超时状态，以及每个返回字段的清洗。验证仍归属快照／差异那一对：[变更 Agent Note](2026-09-09-pkg-mutation.zh.md)为安装与卸载工具保留同一规则，而回滚与对已取回产物的来源验证仍未实现。
