# Agent Note：安装验证比较具名清单快照

Status: implemented

[English](2026-09-09-apps-snapshot-diff.md) | 中文

## 问题

`apps_inspect` 回答「现在装了什么」，但安装器规划的验证步骤需要证明一次安装改变了什么。事后重新读取清单、凭记忆描述差异，产出的是重建的断言而不是证据；规划的观测章节要求具名快照与直接差异。

## 决策

`apps_snapshot` 与 `apps_diff` 加入本包，作为同一个固定采集脚本之上的只读 Consumer。`apps_snapshot` 请求一次审批决定、读取清单，并把完整未过滤的条目集以经过校验的名字保存在组合内存中；存储最多保留 `appsMaxSnapshots` 份捕获，同名捕获替换前一份，超过上限时驱逐最旧的一份。来源全部读不到的捕获会被拒绝而不是保存，因为空基线之后会把每个条目都报告为新增。

`apps_diff` 按稳定的来源键派生 id 匹配条目，因此被改名的应用程序是一条 `changed` 条目，而不是一次新增加一次移除；它报告 `added`、`removed` 以及被比较字段（名称、版本、发布者、安装位置）的逐字段 `changed` 行。它把已存快照与当前机器比较——一次审批决定，并复用清单缓存——或与另一份已存快照比较，后者不读取任何东西，因此不请求任何东西。两个结果都携带各自观测的来源报告与 `coverageChanged` 标志；当两次观测没有覆盖相同的来源时，渲染文本会说明这一点，因为此时条目可能在没有机器变化的情况下显示为新增或移除。存储按会话所有且不持久：捕获属于发起它们的会话，同一组合中的第二个会话读不到它们，`apps_diff` 对未知名字明确失败，而不是拿空基线比较。

## 考虑过的替代方案

**为快照引入持久会话事件。** 延后：这能让捕获跨重启存活，但条目集是机器敏感的元数据，届时会留在会话日志里；模型可见的差异已经作为工具结果被记录，后续切片可以在自己的留存规则下补上持久化。

**按显示名匹配条目。** 否决：名称可变且会在不同产品间重名，会把一次改名变成一次虚假的新增加移除。

**每次 `apps_inspect` 调用自动捕获基线。** 否决：隐式状态会让差异依赖模型没有声明的调用历史；显式名字让基线在日志里可见。

## 后果

安装流程可以捕获基线、执行获批的变更，然后用直接证据把机器与基线做差异，并指明改了什么。覆盖差异会被报告，而不会被悄悄归因于机器；对抗用例钉住了差异的身份规则、对未读取基线的拒绝、存储上限，以及两份已存快照之间的不读取路径。快照会随宿主重启丢失，存储也受界；这两点在包 README 的限制章节中都有说明。
