# Agent Note：包管理器探测是逐探测审批之后的固定命令

Status: implemented

[English](2026-09-09-pkg-inspect.md) | 中文

## 问题

注册表卸载项看不到只在包管理器自身状态里记录的软件包（全局 npm 树、pip 环境、winget 的清单库），而安装器规划的 3b 切片正是要这份清单。读取它意味着执行包管理器，也就是规划中的执行面：它需要逐探测的审批决定、参数注入的防御，以及不会被恶意注册源变成指令的输出处理。

## 决策

`pkg_inspect` 为每个管理器运行一条固定的、由本包拥有的探测命令：`winget list --disable-interactivity --accept-source-agreements`、`npm ls -g --depth=0 --json`、`pip list --format=json`。模型只选择要探测的管理器与结果上限；任何命令文本或参数都不会来自模型输入，参数 schema 的 enum 加上一次校验会拒绝其他管理器名。每次探测经子进程 seam 解析可执行文件、向 `ctx.approval.request` 请求一次性决定（理由指明确切解析出的命令行），只有 `allowed-once` 才会启动任何东西——被拒绝报告为 `denied` 且不产生进程，解析不到可执行文件报告为 `unavailable` 且不请求审批。

输出按流与 `pkgTimeoutMs` 受界；解析器在捕获文本上运行，包名与版本经过共享的字段清洗器，因此控制字符、双向覆盖符与零宽字符会被剔除、过长值会被截断。包身份是管理器与其自身键的摘要，因此显示名变化不会造出第二个包。每个管理器报告自己的状态（`ok`、`partial`、`unavailable`、`denied`、`failed`）与原因，没有读到的管理器会出现在 `coverage.notCovered` 中，而不是被当成「没有安装任何包」。

`chocolatey` 与 `scoop` 有意不探测。它们在本机没有输出证据，未经验证的解析器会把猜测当成清单；要加入它们，先要采集它们的真实输出。

## 考虑过的替代方案

**让模型传入命令或参数。** 否决：那会把只读工具变成任意执行，并使审批理由失去意义。固定 argv 让执行面由本包拥有。

**按固定字符偏移解析 winget 表格。** 否决：表格按显示宽度填充，含双宽字符的行会让之后每一列错位。按列填充（两个及以上空格）切分可让这些行保持对齐，而没有可识别表头的表格会被报告为 partial 而不是猜测。

**通过 shell 工具运行这些管理器。** 否决：shell 字符串是自由文本，而本切片需要每条固定命令一次审批、理由里带确切可执行文件。

## 后果

模型无需提供命令行就能回答「这个管理器知道哪些包」，被拒绝的管理器可证明是惰性的。本切片的对抗门禁钉住了拒绝路径（不产生进程）、实际启动的固定 argv、对注入形管理器名的拒绝，以及包文本的清洗；真实组合测试经本地子进程 provider 读取真实管理器。安装器剩余的工作——propose-confirm-install-verify-rollback 流程——现在既有清单也有了验证原语。
